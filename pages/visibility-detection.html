99% Visible: GPU-based Visibility System in “A Search For a Shiny Thing”

Introduction

In 2024 I co-founded a tiny indie studio called The Notlanders and for the next two years I worked on a photography adventure game under the working title “A Search for a Shiny Thing”. Although the project is currently on indefinite hiatus, it's development presented many interesting challenges and the tech behind the photography system I developed for the game remains one of the pieces of work I'm most proud of. One of our key design goals for photography was accuracy. We wanted the game to understand not just what the player had photographed, but how well they had photographed it. In this article, I will walk you through the GPU-driven solution I developed to make that possible.

The Problem

Most photography games need a way to determine what the camera "sees" when it takes a photo. Let's call this the visibility system. The purpose of a visibility system, thus, is to identify which objects are visibile within the camera's frame and gather information about each of them. We wanted the system to work with many different types of objects: characters, buildings, graffiti, plants, etc. It was important for us not only to know whether the object is visible, but how much of it is visible. If only 15% of a lighthouse appears in the frame, the game should acknowledge that the player photographed it, while also recognizing that it was only partially captured.

The obvious question is: how do you actually implement that?

Let's step away from photography for a second and look at how games implement AI sight perception. A typical implementation would first perform a broad-phase cull based on distance and NPC's field of view. If the player falls within the NPC's view cone, the game performs line-of-sight checks by casting rays toward visibility points on the character (typically bones). Depending on how many rays hit the target without being occluded, the player is considered (in)visible. This approach works extremely well for certain genres, particularly stealth games, and unsurprisingly many photography games do something very similar.

For our use case, raycasting had two major shortcomings. From a workflow perspective, it would require a significant amount of tediuos manual labour, unless we come up with a system to automatically assign visibility points to objects. I briefly considered making such a tool, but balancing accuracy and performance quickly became a concern.

The second issue is that raycasting only measures visibility. In real-life photography, getting the subject into the frame is only part of what makes a good photograph. Lighting, focus, and composition also influence the result, and we wanted to use these elements to create interesting gameplay scenarios. Ideally, in-game photography should have enough depth to be a fun toy to play with on its own. Building separate systems for evaluating lighting and focus was certainly possible, but after some experimentation I thought of a way to solve several problems at once.

The Solution

There must be a way to do this on the GPU, I thought. It has a lot of advantages, if you think about. Thanks to depth testing, the fragment shader will only render the visible fragments. Many objects can be processed in parallel. Additional information like lighting data can be accessed at the same time. What does it mean to see an object though? When we're talking about quantifiying how much of the object is visible we are essentially talking about the visible surface area. Calculating the surface area of an arbitrary shape sounds complicated, but there are a couple of ways to simplify this problem by converting it from 3D to 2D. One of those ways is UV mapping. You take the 3D model's surface and convert it to a 2D plane, which can be rendered as a texture, providing us with a reference point of what 100% visibility is. All that remains is to write which fragments are visible to a texture and compare it with the reference. Luckily, since shader model 5, it's possible to write to a UAV (unordered access view, i.e. random read/write) texture from a fragment shader. As for comparing it with a reference, that can be done using a compute shader which we can dispatch in a custom render pass and request to read the results asynchronously.

Here is how it works step by step (simplified):

  1. An artist prepares a simplified visibility mesh with custom UV mapping and renders the UVs as a low-res texture to serve as reference.
  2. Broad-phase culling is handled by using Unity's OnBecameVisible and OnBecameInvisible build-in messages. A photographable object adds itself to a list when visible.
  3. Based on it's position in the list, each candidate for visibility photographable object is assigned an ID, which is passed to the GPU as a uniform.
  4. A custom render pass sets a random write target, which is a RWTexture2DArray.
  5. The custom render pass filters and draws every candidate photo object in a batch.
  6. The fragment shader writes visible fragments to a slice of the texture array using it's custom UVs, the reference size and previously passed ID
  7. The render pass dispatches a compute shader, which adds together all visible pixels for each slice of the texture array.
  8. The render pass requests asynchronous readback from the GPU.
  9. When the read reqeust is complete, compare currently visible pixels to maximum visible pixels and if the visibility is greater than 0 add the object to a "currently in frame" list.

This is what the fragment shader looks like, simplified. I didn't include the lengthy section of code that deals with lighting calculations. Ideally, I would simply do a lambertian diffuse, but it's more complicated because I have to include baked lighting, and the light color won't always be white. To resolve that issue, I conver the linear RGB color to luminance, and then to percieved lightnightss (CIELAB L*). The last step is optional, but it makes the lightness measure appear more correct to human eyes. Calculating focus is simpler, using Unity's depth of field post-processing feature you can directly sample the circle of confusion texture. The value needs to be remapped because Unity encodes 0.5 as being most in focus, and 0 and 1 represent full near and far blur respectively.

RWTexture2D<float2> output;

[earlydepthstencil]
float3 frag(v2f i) : SV_Target
{
    ...

    float lightness = ColorToLStar(color);
    float focus = SampleCoCTexture(i.positionNDC.xy / i.positionNDC.w);

    uint2 pixel = uint2(i.uv * _ReferenceSize);
    output[pixel] = float2(lightness, focus);

    // return debug color
}

You may have spotted a curious [earlydepthstencil] in the code above, which is included for a reason. Early on when I was protyping the visibility system I ran into a difficult bug. When I checked the output texture I could see that fragments that shouldn't be visible were being rendered, which put the whole idea in doubt. If I looked at an object from a perspecive where one part of the object obscured another part of the object for whatever reason I could still see the fragments that should've been discarded in a early-z test still being rendered. If you've done some graphics programming, you might know that writing to depth disables early-z. That makes sense because the GPU can't know for sure if the depth value is going to remain the same. Well, as it turns out, for whatever reason if you write to UAV texture early-z is also gets disabled by default. I couldn't find out why it happens (it was difficult enough to discover what's going on in the first place), so if you know please let me know. Thankfully, [earlydepthstencil] attribute allows you to force early depth-stencil testing.

Conclusion

The result is a system that can calculate with relative accuracy not only what % of the object is visible but also how well lit it is and whether it's in focus. All that in real-time and able to scale well into tens of objects and stay under 1ms cost. While the photography system has been battle tested in internal and external playtests, it's by no means fully complete and there's additions and improvements to be made before it's ready for release. Having said that, I'm quite proud of it. To my best knowledge, nobody has ever done anything like this before, which kind of made me feel like an explorer.

Future Work

There is a potential alternative approach I've been thinking about that doesn't add the additional steps of making custom UVs and exporting a reference texture. Since meshes are composed of triangles, it's trivial to calculate it's surface area. If you render the SV_PrimitiveID (assuming the order is same as on the CPU and stable across frames) into an offscreen buffer, in theory, one can then calculate the surface area of the visible triangles. No need for a UAV texture this time. My concern here would be that you'd have to iterate over hundreds of thousands of pixels, deduplicate the triangles and calculate (or look up) and sum up the surface area of each of them. Given the real-time requirement, it would be too expensive on the CPU, but if I could perform the deduplication step in a compute shader it might be a viable approach.
